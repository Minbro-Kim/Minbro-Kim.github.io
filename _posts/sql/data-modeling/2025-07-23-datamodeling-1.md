## 1. 모델링의 이해

### 가. 모델링 정의

- 복잡한 현실세계를 일정한 표기법에 따라 표현하는 일

### 나. 모델링 특징

1. 추상화(모형화, 가설적): 다양한 현상을 일정한 양식인 표기법에 따라 표현
2. 단순화: 복잡한 현실세계를 제한된 표기법이나 언어로 표현하여 이해를 도움
3. 명확화: 애매모호함을 제거하고 정확하게 현상 기술

→ 현실세계를 추상화, 단순화, 명확화하기 위해 일정한 표기법에 의해 표현하는 기법

### 다. 모델링의 세 가지 관점

1. <mark>데이터 관점(What, Data)</mark>: 업무와 데이터, 데이터 간의 관계에 대해 모델링하는 방법
2. 프로세스 관점(How, Process): 업무가 무엇인지, 무엇을 해야 하는지 모델링하는 방법
3. 데이터와 프로세스의 상관 관점(Interaction): 업무 처리 방법에 따라 데이터가 어떻게 영향 받는지 모델링하는 방법

## 2. 데이터 모델의 기본 개념 이해

### 가. 데이터 모델링 정의

- 정보시스템을 구축하기 위한 데이터 관점의 업무 분석 기법
- 현실세계의 데이터(what)에 대해 약속된 표기법에 의해 표현하는 과정
- 데이터베이스를 구축하기 위한 분석·설계의 과정

### 나. 데이터 모델이 제공하는 기능

- 시스템을 현재 또는 원하는 모습으로 가시화
- 시스템의 구조와 행동을 명세화
- 시스템을 구축하는 구조화한 틀 제공
- 시스템 구축 과정에서 결정한 것을 문서화
- 다양한 영역에 집중하기 위해 다른 영역의 세부 사항은 숨기는 다양한 관점 제공
- 특정 목표에 따라 구체화한 상세 수준의 표현방법을 제공

## 3. 데이터 모델링의 중요성과 유의점

### 가. 데이터 모델링이 중요한 이유

1. 파급효과(Leverage)
    - 단위·병행·통합 테스트 과정에서 데이터 모델의 변경이 필요한 경우, 다양한 영향 분석 후 변경작업 → 전체 시스템 구축 프로젝트에서 위험요소
2. 복잡한 정보 요구 사항의 간결한 표현(Conciseness)
    - 데이터 모델을 통해 구축할 시스템의 정보 요구사항과 한계를 파악 LIKE 설계도면
3. 데이터 품질(Data Quality)
    - 중복 데이터의 미정의, 데이터 구조에서 비즈니스 정의의 불충분, 동일한 성격의 데이터를 통합하지 않고 분리함으로써 나타나는 데이터 불일치 등의 데이터 구조의 문제로 데이터 품질 문제가 발생 → 바로잡기 어려움

### 나. 데이터 모델링 시 유의점

1. 중복
    - 여러 장소에 같은 정보를 저장 → 데이터 불일치, 유지보수의 어려움
2. 비유연성: 데이터 모델 변경
    - 데이터 모델 변경이 어려움 → 유지보수의 어려움
    - 데이터의 정의를 데이터의 사용 프로세스와 분리 필요
3. 비일관성
    - 다른 데이터와 모순을 고려하지 않고 일련의 데이터 수정 → 비일관성 발생
    - 데이터의 중복이 없더라도 발생 가능(신용 갱신 없이 납부 이력 갱신)
    - 데이터 간 상호 연관 관계에 대한 명확한 정의 필요

### 가. 개념적 데이터 모델링(Conceptual Data Modeling)

- 조직과 사용자의 데이터 요구사항을 탐색·분석
- 핵심 엔터티와 그 관계 발견 및 표현 → 엔터티-관계 다이어그램(ERD) 생성
    - ERD는 조직과 사용자에게 어떤 데이터가 중요한지 시각적으로 표현
- 현 시스템이 어떻게 변형되어야 하는가를 이해하는 데 유용
- 개념적 데이터 모델링을 전 조직에 걸쳐 진행한 것이 전사적 데이터 모델(Enterprise Data Model)

### 나. 논리적 데이터 모델링(Logical Data Modeling)

- 데이터베이스를 설계 시, 업무 정보의 논리적 구조와 규칙을 쉽게 이해할 수 있도록 표현하는 방법
- 상세화 과정: 식별자 확정, 정규화, N:N 관계 해소, 참조 무결성 규칙 정의, 이력 관리 전략 수립
- 논리적 데이터 모델은 데이터 모델링이 최종적으로 완료된 상태

  → 물리적 스키마 설계를 하기 전 단계의 데이터 모델 상태


### 다. 물리적 데이터 모델링(Physical Data Modeling)

- 논리 데이터 모델을 기반으로 물리적 스키마를 설계 하는 과정
    - 물리적 스키마: 데이터가 물리적으로 컴퓨터에 어떻게 저장·접근될 것인가에 대한 정의
- 테이블, 컬럼 등 물리적 저장 구조와 사용할 저장장치(디스크, SSD 등), 데이터 접근 방법(인덱스, 파티션 등)을 결정
- DBMS의 특성(Oracle, MySQL 등)에 맞춰 최적화하는 작업 포함
- 계층적 데이터베이스 관리 시스템 환경에서는 데이터베이스 관리자가 물리적 스키마를 설계하고 구현하기 위해서 더 많은 시간 투자

## 5. 프로젝트 생명주기에서의 데이터 모델링

- 현실 프로젝트에서는 대부분 개념적 데이터 모델링과 논리적 데이터 모델이 같이 수행
- 폭포수(Waterfall) 모델에서의 데이터 모델링 위치
    - 분석 단계 - 논리적 데이터 모델링
    - 설계 단계 - 물리적 데이터 모델링
- 나선형 모델, RUP(Rational Unified Process)에서의 데이터 모델링 위치
    - 업무 크기에 따라 논리적 데이터 모델과 물리적 데이터 모델이 분석·설계 단계 양쪽에서 수행
    - 일반적으로 분석 단계에서 논리적 데이터 모델링이 많이 수행
- 데이터 축과 애플리케이션 축으로 구분하여 프로젝트를 진행하면서 각각 모델링 전개
    - 객체지향 개념은 데이터 모델링과 프로세스 모델링을 구분하지 않고 일체형으로 진행(Class 개념)

## 6. 데이터 모델링에서의 데이터 독립성의 이해

### 가. 데이터 독립성의 필요성

- 데이터 독립성 ↔ 데이터 종속성
    - Application(응용)에 종속되어 데이터가 있는 파일과 데이터에 접근하기 위한 인덱스를 별도로 구현하여 사용자가 접근하는 방법(트랜잭션(업무 작업)의 유형)에 따라 데이터를 구성하는 방법이 영향을 받음
        - 어떤 트랜잭션은 `고객 ID + 주문 내역`만 조회, 어떤 트랜잭션은 `고객 이름 + 주소`를 자주 조회 → 과거 파일 방식은 이에 대해 일일이 데이터를 구성
- 유지보수 비용 절감
- 데이터 복잡도↓
- 중복된 데이터↓
- 화면과 데이터베이스 간의 독립성 유지 → 사용자 요구사항 대응 유리
- 데이터 독립성 효과
    - 각 뷰(View)의 독립성을 유지 & 계층별 뷰에 영향을 주지 않고 변경 가능
    - 단계별 스키마(Schema)에 따라 데이터 정의어(DDL)와 데이터 조작어(DML)가 다르게 정의될 수 있는 구조를 제공

### 나. 데이터베이스 3단계 구조

- ANSI/SPAR(앤시 스팍)의 3계층 모델
    - 외부, 개념, 내부 단계가 분리되어 서로 간섭하지 않고, 이를 통해 데이터 독립성을 실현하는 표준 데이터베이스 구조 모델
    - 외부 단계: 사용자가 처리하고자 하는 데이터 유형·관점·방법에 따라 다른 스키마 구조
    - 개념 단계: 사용자가 처리하는 데이터 유형의 공통적인 사항을 처리하는 통합된 뷰를 스키마 구조로 디자인, 통상적 데이터 모델
    - 내부 단계: 데이터가 물리적으로 저장된 방법에 대한 스키마 구조

![img.png](/assets/images/posts_img/sql/datamodeling/sql-4.png)

## 9. 데이터 모델의 표기법인 ERD 이해

### 가. 데이터 모델 표기법

- 1976년 피터첸 (Peter Chen)이 E-R모델(Entity-relationship medel) 표기법 개발
- IE 표기법과 Barker 표기법이 주로 사용됨

### 나. ERD 표기법으로 모델링하는 방법

- ERD(Entity Relationship Diagram)
    - 엔터티와 엔터티 간의 관계를 도식화된 다이어그램으로 표시
    - 데이터 흐름과 프로세스의 연관성을 표현하는 표기법·산출물
1. ERD 작업 순서
    - Entity - 사각형
    - Primary Key & Foreign Key - ERD 규칙

   ① 엔터티 그리기

   ② 엔터티 배치

   ③ 엔터티 간 관계 설정

   ④ 관계명 기술

   ⑤ 관계 참여도 기술

   ⑥ 관계 필수 여부 기술

2. 엔터티 배치
    - 중요한 순서로 왼쪽 → 오른쪽, 위쪽 → 아래쪽 방향
    - 가장 중요한 엔터티 - 왼쪽 상단 조금 아래 중앙에 위치 → 다른 엔터티와의 관계 설정 용이

   ![img.png](/assets/images/posts_img/sql/datamodeling/sql-9.png)
   *▲ 엔터티 배치 방법*

3. ERD 관계의 연결
    - 관계를 정의한 분석서를 통해 엔터티 간의 관계 설정
    - <mark>초기에는 Primary Key로 속성이 상속되는 식별자 관계 설정</mark>
    - 중복 관계 X, Circle 관계X

   ![img.png](/assets/images/posts_img/sql/datamodeling/sql-10.png)
   *▲ ERD 관계 설정*

4. ERD 관계명의 표시
    - 연결된 관계에 관계 이름 부여
    - 관계 이름 - 현재형, 포괄적용어(이다, 가진다)사용 X
    - 실제 프로젝트에서는 크게 고려하지 않아도 ERD 흐름 파악 가능

   ![img.png](/assets/images/posts_img/sql/datamodeling/sql-11.png)
   *▲ ERD 관계명 표시*

5. ERD 관계 관계차수와 선택성 표시
    - 관계차수(Cardinality) 표현
        - 카티널리티: 두 개체(Entity) 간의 관계에서 각각이 몇 개의 인스턴스를 가질 수 있는지를 나타내는 개념
            - Cardinality 자체가 원소의 개수를 의미 → 테이블에서는 행의 수
        - IE 표기법:  하나(1, One) 관계 - 실선, 다수(Many)관계 - 까마귀발, 필수·선택 표시 - 관계선에 원 추가

          ![img.png](/assets/images/posts_img/sql/datamodeling/sql-12.png)

        - Barker 표기법: 필수·선택 표시 - 실선, 점선으로 표기

## 10. 좋은 데이터 모델의 요소

- 데이터 모델의 객관적 품질 평가 지표 X → 대체적으로 긍정적으로 평가할 수 있는 요소(완전성, 중복배제…)

### 가. 완전성(Completeness)

- 업무에 필요한 모든 데이터가 데이터 모델에 정의
- 기초적 평가 요소

### 나. 중복배제(Non-Redundancy)

- 한 데이터베이스 내에 동일한 사실은 반드시 한 번만 기록(ex. 생년월일-나이)
- 데이터 관리 비용(저장공간 등) 낭비 방지

### 다. 업무 규칙(Business Rules)

- 업무 규칙을 데이터 모델에 표현 및 모든 사용자와 공유
- 특히, 논리 데이터 모델에서 중요
- ex. 모든 사원들은 월별 하나 이상의 급여를 지급받고, 급여는 사원의 종류에 따라 결정

### 라. 데이터 재사용(Data Reusability)

- <mark>통합</mark> 모델 → 재사용성↑
- 데이터가 애플리케이션에 대해 <mark>독립적으로 설계</mark> → 재사용성↑
- 외부 업무 환경 변화에 유연하게 대응하기 위한 확장성 확보 필요 → 데이터 관점의 통합 필요
    - 행위 주체가 되는 집합의 통합, 행위 대상이 되는 집합의 통합, 행위 자체에 대한 통합 → 안전성, 확장성

### 마. 의사소통(Communication)

- 데이터 분석 과정에서 도출된 업무 규칙들은 엔터티, 서브타입, 속성, 관계 등의 형태로 데이터 모델에 구체적으로 표현 → 관련자들이 동일한 이해를 바탕으로 활용
- ex. 사원의 종류(정규직, 임시직), 정규직만 급여 테이블과 관계

### 바. 통합성(Integration)

- 고객, 상품 등의 마스터 성격의 데이터의 분할·관리 → 데이터의 품질, 관리, 활용에 문제 발생
- 조직 전체에서 한 번만 정의되고 이를 참조·활용하는 것이 바람직
    - 공유 데이터에 대한 구조를 공동 사용이 용이하게 설계 필요 → 데이터 아키텍처 중요
    - 성능 목적 등으로 데이터 중복O
