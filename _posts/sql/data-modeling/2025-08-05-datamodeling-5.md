## 1. 식별자 개념

- 하나의 엔터티에 구성된 여러 개의 속성 중 <mark>엔터티를 대표할 수 있는 속성</mark>
- 하나의 엔터티는 <mark>반드시 하나의 유일한 식별자가 존재</mark>
- <mark>식별자 ≠ 키</mark>
    - `식별자`는 업무적으로 구분되는 정보로, 논리 데이터 모델링 단계에 사용
    - `키(Key)`는 데이터베이스 테이블에 접근하기 위한 매개체로, 물리 데이터 모델링 단계에 사용

---

## 2. 식별자의 특징

- `유일성`
    - 주식별자에 의해 엔터티 내의 모든 인스턴스들이 유일하게 구분
    - ex. 고유한 사원번호
- `최소성`
    - 주식별자를 구성하는 속성의 수는 유일성을 만족하는 최소의 수
    - ex. 사원번호만으로 구분이 되는데 사원부류코드를 추가하여 식별자가 구성되는 것은 부적합
- `불변성`
    - 지정된 주 식별자의 값은 자주 변하지 않음
    - ex. 사원번호의 값이 변한다는 것은 이전 기록의 말소 및 새 기록의 생성을 뜻함
- `존재성`
    - 주식별자가 지정되면 반드시 값이 있어야 함(Null X)
    - ex. 모든 사원은 사원번호를 가짐
- 대체 식별자는 주식별자의 특징과 같지만, 외부식별자의 경우 `참조무결성(Referential Integrity)` 특징을 가짐

---

## 3. 식별자 분류 및 표기법

### <mark>가. 식별자 분류</mark>

- 엔터티 내의 대표성
    - `주식별자(Primary Identifier)`: 각 어커런스를 구분할 수 있는 구분자, 타 엔터티와 참조관계 연결 시 이용
    - `보조식별자(Alternate Identifier)`: 각 어커런스를 구분할 수 있으나, 대표성이 없어 참조관계 X
- 엔터티 내에서 생성 여부
    - `내부식별자(Internal Identifier)`: 엔터티 내부에서 스스로 만들어지는 식별자
    - `외부식별자(Foreign Identifier)`: 타 엔터티로부터 받아오는 식별자
- 속성 수
    - `단일식별자(Single Identifier)`: 하나의 속성으로 구성된 식별자
    - `복합식별자(Composit Identifier)`: 둘 이상의 속성으로 구성된 식별자
- 기존 식별자 대체 여부
    - `본질식별자(Natural Identifier)`: 업무에 의해 만들어지는 식별자
    - `인조식별자(Artificial Identifier)`: 원조식별자의 복잡한 구성을 대체하여 인위적으로 만든 식별자 → 일련번호

### 나. 식별자 표기법

- 네가지 분류를 모두 표기

## 4. 주식별자 도출기준

1. 해당 업무에서 자주 이용되는 속성을 주식별자로 지정
    - 직원 엔티티에서 사원번호를 주식별자, 주민등록번호를 보조식별자로 사용
2. 명칭, 내역 등과 같이 이름으로 기술되는 것은 피함
    - 부서 이름이 유일하다고 주식별자X, 조회 시 긴 이름 조건절에 기술해야하는 문제

   → 새로운 식별자 생성(ex. 일련번호, 코드)

   → 부서코드를 부여하여 코드엔터티에 등록 후, 주식별자로 지정 또는 부서번호를 주식별자로, 부서명을 보조식별자로 활용

3. 속성의 수가 많아지지 않도록 함
    - 일반적으로 7~8개 이상의 속성으로 구성된 주식별자는 인조식별자 생성 권장 → 조인 편리
    - ex. 접수번호 = 관할부서 + 접수일자 + 일련번호

## 5. 식별자 관계와 비식별자 관계에 따른 식별자

### 가. 식별자 관계와 비식별자 관계의 결정

- <mark>외부식별자는 데이터베이스 생성 시 FK 역할</mark>
- 자식엔터티에서 부모 엔터티로 온 외부식별자를 주식별자로 이용할 것인지 결정 → 식별/비식별자 관계
- 업무 특징, 자식엔터티의 주식별자 구성, SQL 전략을 고려하여 결정

### <mark>나. 식별자 관계(Identifying)</mark>

- <mark>부모로부터 받은 식별자를 자식엔터티의 주식별자로 이용</mark> → 부모엔터티가 필수로 존재
- 1:1 관계
    - 부모의 주식별자를 자식 엔터티의 주식별자로 단독 사용
    - 엔터티 통합 대상
    - ex. 사원-사원번호 → 임시사원-사원번호
- 1:M 관계
    - 부모의 주식별자에 별도의 속성(자신 또는 다른 부모 엔터티 속성)을 더하여 주식별자로 사용
    - ex. 사원-사원번호 → 발령-사원번호+발령일자

### <mark>다. 비식별자 관계(Non-Identifying Relationship)</mark>

- <mark>부모 엔터티로부터 속성을 받았지만 주식별자로 사용하지 않고 일반적 속성으로만 사용</mark>

    1. 부모 속성이 필수가 아니어서 부모 없는 자식이 생성될 수 있는 경우
    2. 엔터티별로 데이터의 생명주기(Life Cycle)을 다르게 관리할 경우
    3. 여러 엔터티의 통합·표현함에 따라 각 엔터티가 별도의 관계를 가지는 경우
        - 인터넷회원-아이디, 전화회원-전화번호 → 접수-접수번호(아이디, 전화번호)
    4. 자식엔터티에서 별도의 주식별자의 생성이 더 유리한 경우
        - 사원-사원번호 → 계약-계약번호(계약사원번호)

### 라. 식별자 관계로만 설정할 경우의 문제점

- 1:M 관계에서 식별자 관계로 연결될 경우 자식엔터티의 주식별자는 (부모 PK속성수 + 1)로 속성 수 증가

  → 개발 복잡성이 높아지고 오류 유발


### 마. 비식별자 관계로만 설정할 경우의 문제점

- 자식엔터티에서 부모속성을 조회조건으로 사용할 경우 부모엔터티까지 조회 필요

  → 불필요한 조인 및 구문 길이 증가, 성능 저하


### 바. 식별자 관계와 비식별자 관계 모델링

**a) 비식별자관계 선택 프로세스**

- 식별자관계로 기본 설정 → 조건에 따라 비식별자관계로 조정
    - 약한 관계
    - <mark>독립 PK 구성 필요(업무적 필요성 + 성능적 필요성)</mark>
    - SQL복잡도 증가/개발생산성 저하

  → 비식별자 관계 설정 고려
