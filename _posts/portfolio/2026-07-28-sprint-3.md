## 1. 프로젝트 개요

- **서비스 명**: <mark>글로벌 컨텐츠 평점 및 실시간 소통 플랫폼</mark>
- **목적**
  - 다양한 콘텐츠 목록을 제공하고, 플레이리스트를 공유하며 실시간 같이 보기를 지원하는 서비스 구축
- **주요 기능**
  - 영화, 드라마, 스포츠 등 다양한 콘텐츠 수집 및 리뷰 등록
  - 플레이리스트 생성 및 공유, 구독 서비스
  - 실시간 같이 보기 기능 및 채팅 지원
  - 사용자 맞춤형 알림 서비스 제공


## 2. 담당 작업

- **Websocket 연결 관리**: Websocket 사용자 인증 및 Event 기반 연결 관리 구현
- **시청세션 관리**: STOMP 프로토콜을 활용한 실시간 시청 세션 관리 및 저장(In-Memory/Redis)
- **시청 세션 API**: 같이 보는 시청자 목록 및 특정 사용자의 시청 정보 조회 API 구현
- **Redis Pub/Sub**: Redis Pub/Sub을 활용한 분산환경에서의 실시간 같이보기 메세지 전달 구현
- **Kafka 연동**: Kafka를 활용한 비동기 이벤트 처리

## 3. 기술적 성과
- **Websocket 연결 관리**
  - STOMP 프로토콜을 활용하여 Websocket 연결 시 사용자 인증 및 세션 관리 구현
  - Websocket 연결 종료 시, 관련 세션 정보 및 구독 정보 정리
- **Redis 저장소 활용**
  - 시청 정보를 Redis에 저장하여 DB 부하를 최소화하고, 빠른 조회
  - Redis Pub/Sub을 활용하여 분산 환경에서도 실시간 같이보기 메시지 전달 가능
- **Kafka 연동**
  - 시청세션 변경 이벤트를 Kafka를 통해 비동기적으로 처리하여 유실 방지 및 확장성 확보
  - Kafka Consumer를 통해 시청세션 변경 이벤트를 수신하고, Redis pub/sub으로 메세지 전달
- **추상화를 통한 다양한 기술 지원**
  - 시청세션 저장소를 추상화하여 In-Memory, Redis 등 다양한 저장소 지원
  - Kafka와 기본 Event 기반 처리 방식을 추상화하여, 필요에 따라 선택적으로 적용 가능

## 4. 문제 해결 과정

### [문제 1] 로그아웃 시 Websocket 연결 종료 및 시청세션 정리

- **상황**
  - 클라이언트가 로그아웃 시, 명시적으로 웹소켓(STOMP) 연결을 해제하지 않아 서버에 세션이 좀비 상태로 유지
  - 살아있는 이전 세션 때문에 다른 계정으로 재로그인 시 이전 사용자의 세션 정보나 채팅/웹소켓 설정이 그대로 이어지는 보안 및 데이터 정합성 결함 발생
- **분석**
  - 스프링의 SubProtocolWebsocketHandler는 내부적으로 WebSocketSession을 private Map으로 관리하고 있어, 외부 클래스에서 세션 ID만으로 물리적 세션에 직접 접근(close())할 수 없는 구조적 한계
  - 프론트엔드가 연결을 끊지 않을 때 서버가 주도적으로 특정 사용자의 소켓을 강제 종료할 수단 부재
- **해결**
  - 대안 1 (웹소켓 세션 별도 저장)
    - Handshake 시점에 세션을 내부메모리에 저장
    - 장점: close() 명령어로 직접 연결 종료 가능
    - 단점: 생명주기를 직접 동기화해야 하고 다중 서버 환경에서 구현 복잡도 상승

  - ✅ 대안 2 (STOMP ERROR FRAME 활용)
    - 스프링 내부의 clientOutboundChannel을 통해 StompCommand.ERROR패킷 전송
    - 장점: 스프링이 ERROR 프레임을 수신할 때 내부적으로 session.close()를 호출하는 메커니즘을 이용해, 별도의 세션 저장소 관리 없이 강제 종료
    - 단점: 웹소켓 종료 코드가 1002
- **결과**
  - 프론트엔드의 명시적 요청 없이 서버 주도로 특정 사용자의 웹소켓 세션 강제 종료(CloseStatus[code=1002])
  - SessionDisconnectEvent가 정상적으로 트리거되어 세션 및 관련 리소스가 정리됨으로써 계정 전환 시의 데이터 오염 문제 차단
  
  ```text
  [http-nio-8080-exec-5] DEBUG c.t.m.c.w.l.WebSocketLogoutDisconnectListener - [LOGOUT EVENT] Disconnecting userId: db36bed6...
  [ws-heartbeat-thread-1] DEBUG o.s.w.s.s.t.s.WebSocketServerSockJsSession - Closing SockJS session 5h3bpg5o with CloseStatus[code=1002, reason=null]
  [ws-heartbeat-thread-1] DEBUG c.t.m.w.l.WatchingSessionEventListener - [EVENT TRACE] SessionDisconnectEvent 수신 완료: sessionId=5h3bpg5o
  ```

### [문제 2] 시청 세션 비정규화(스냅샷)를 통한 조회 성능 최적화
- **상황**
  - 기존에 실시간 같이보기 목록 조회 시, 시청 세션 정보와 사용자 프로필 정보를 매번 별도로 조회해야 하므로 대규모 동시 접속 시 쿼리 병목 및 성능 저하 우려
- **분석**
  - 시청 세션은 콘텐츠 화면에 입장(생성)하는 순간 유효하며, 해당 시점의 사용자 정보는 퇴장(구독해제)까지 변경되지 않는 특성이 있음
- **해결**
  - 시청 세션 생성 시점의 사용자 정보를 세션 데이터에 함께 스냅샷(비정규화) 형태로 캐싱 및 저장하도록 구조 개선
  - 목록 조회 시 추가적인 DB 조인이나 매핑 없이 세션 정보만으로 즉시 반환되도록 최적화하고, 실시간 채팅에서도 해당 사용자 정보를 곧바로 활용할 수 있도록 설계
- **결과**
  목록 조회 과정의 불필요한 연산 및 DB 부하를 대폭 줄이고 실시간 응답 성능 개선
- 관련 PR 및 이슈
  - [관련 PR](https://github.com/sb10-team06/sb10-moduply-team6/pull/272)

## 6. 코드 품질 및 최적화

### 1) Kafka Event 처리 최적화

- **상황**
    - 기존에 Spring Event 기반으로 처리하던 비동기 이벤트를 Kafka로 일부 전환
- **분석**
  - 기존 이벤트 구조를 유지하면서 최소한의 코드 변경으로 Kafka 연동을 위해 Event 구조를 추상화
- **해결**
  - Kafka Event Interface를 정의하고, 기존 Event 클래스가 이를 구현하도록 변경
  - KafkaProduceRequiredEventListener를 구현하여 해당 이벤트를 Kafka로 전송하도록 처리
  - Kafka Consumer에서 해당 이벤트를 수신하고, 기존 EventListener의 로직을 processor로 변경하고 기본 event listener와 kafka event listener를 property에 따라 선택적으로 등록하도록 구현
- **결과**
    - 기존 Event 구조를 유지하면서 Kafka 연동 가능
    - Kafka를 통한 비동기 이벤트 처리로 확장성 확보 및 유실 방지
    - 기본 Event 처리와 Kafka Event 처리를 선택적으로 적용 가능
- 관련 PR 및 이슈
  - [관련 PR](https://github.com/sb10-team06/sb10-moduply-team6/pull/403)
  - [관련 이슈](https://github.com/sb10-team06/sb10-moduply-team6/issues/395)

### 2) In-Memory와 Redis 저장소 전환 시 인터페이스 추상화 및 동기화 설계

- **상황**
  - 개발 초기에는 단일 서버 환경을 고려해 In-Memory 기반으로 시청 세션을 관리했으나, 추후 멀티 서버 확장(Scale-out)을 고려하여 Redis 기반 저장소로 유연하게 전환할 수 있는 구조가 필요해진 상황
- **분석**
  - 비즈니스 로직 코드 내부에 특정 저장소(In-Memory Map 등) 의존성이 강하게 결합되어 있으면, 저장소 변경 시 전면적인 코드 수정이 발생하고 테스트가 어려워지는 문제 발생
- **해결**
  - 시청 세션 저장소 관련 인터페이스(Repository)를 정의하여 역할 분리
  - 구현체로 InMemoryWatchingSessionRepository와 RedisWatchingSessionRepository를 각각 구현
  - 프로퍼티 설정 값(in-memory 또는 redis)에 따라 실행 시점에 적절한 빈(Bean)이 동적으로 주입되도록 구성하고, 기본값(matchIfMissing = true)을 두어 로컬 환경에서의 편의성 확보
- **결과**
  - 비즈니스 로직의 변경 없이 설정 값만으로 시청 세션 저장소를 In-Memory와 Redis 간에 유연하게 전환할 수 있는 확장성 확보

## 7. 향후 개선 사항
- 대규모 트래픽 환경에서의 실시간 성능 모니터링 고도화
  - Redis Pub/Sub과 Kafka 파이프라인 연동 구조에서 다수 사용자가 동시에 입퇴장할 때의 메시지 처리 지연(Latency) 측정
- WebSocket 스케일 아웃(Scale-out) 환경 검증
  - 멀티 인스턴스 환경에서 Redis Pub/Sub 브로드캐스팅 및 세션 정리가 병목 없이 안정적으로 동작하는지 부하 테스트(k6 등)를 통한 검증 추가 진행
- outbox도입으로 유실 이벤트 처리
